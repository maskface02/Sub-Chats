## Top 4 risks — Backend (revocation + restore + export + destructive edits)

1. **deletedAt filter on EVERY conversation-id route (T-E-1 — high).** Soft-delete is an access-revocation surface: the full route list is list / read / tree / export / send / **branch** / **edit** / **regenerate**, plus delete (re-delete → 404) and restore (inverse). The three new ones are exactly where rev-1 of the spec missed the point: **branch-on-deleted** mints an orphan sub-chat whose `parentId` points at a deleted row; **edit-on-deleted** is resurrect-by-write (mutates message history the user believes is gone); regenerate is the same class. Implementation gate: ONE shared live-row lookup helper (`id` + `userId` + `deleted_at IS NULL`) used by every route — no hand-rolled WHERE clauses. Unit tests per AC.5 including branch-on-deleted → 404 and edit-on-deleted → 404. Export is the worst miss (bulk deleted-data exfil into a portable file).
2. **Restore is user-scoped, not batch-trusted (T-E-2 — high).** `deleted_batch_id` is a capability token. The restore UPDATE must carry BOTH predicates: `WHERE deleted_batch_id = :batchId AND user_id = :userId` — the user predicate goes IN the UPDATE (defense in depth), not only in a pre-check. batchId is read server-side from the target row's own `deleted_batch_id` (Reviewer fix #5), never from the request body (which stays `{}`). Cross-user restore must be 404 with the victim's rows untouched — Vitest asserted. Also: restore is idempotent (not-deleted → `restoredCount: 0`), and the cascade's live-only filter (`deleted_at IS NULL`, US-403 AC.2b) is what keeps batch bookkeeping exact across nested deletes — don't "simplify" it away.
3. **Export output encoding — md structure + header injection (T-T-1/T-T-2 — high if unmitigated).** (a) Message content starting with `#`/`---`/a fence is fence-wrapped per US-403 AC.3 (inner fences lengthened) — otherwise a message forges section headers or swallows every subsequent message into a code block in the exported artifact; the adversarial fixture test is a hard gate. (b) The conversation title flows into `Content-Disposition` — strip CR/LF/`"`/`\`/C0-C1 control chars from the slug BEFORE the header (≤ 60 chars, RFC 5987 for non-ASCII). A CRLF in the title is response splitting. The sanitizer must be the only path from title to header. (c) Row scoping: messages query join-predicated on the owner; md breadcrumb walks ancestors with per-iteration ownership checks (phase-1 pattern) — a scoping bug here leaks in bulk, one user's entire conversation in one file.
4. **Destructive-mutation discipline on edit/regenerate (T-T-3, T-R-1, DI-2).** (a) Edit content validation MUST be the send schema — shared zod `.strict()` + 1..8000 constant, not a re-typed literal that drifts (edit otherwise becomes the validation bypass). (b) Both routes are 409-on-streaming, never abort-then-proceed (§8.6) — destructive truncation must not race an in-flight stream. (c) The message hard-DELETEs (truncate tail / regenerate target) are the ONLY hard-deletes in phase 4 (conversations stay soft — grep gate per US-401 AC.9); DI-2 (permanent tail loss, OQ-4) is accepted and documented — do not add message soft-delete. (d) Audit events: delete/restore/edit/regenerate logged with ids + counts + batchId only — NEVER message content, titles, or edited text (redact is pattern-based; an ad-hoc `log.info({content})` slips through — hardening #6).

Also audit-gated: 409 STREAM_ACTIVE checked against the target AND every cascade-set id (AC.6) with the check inside/consistent with the delete transaction (hardening #5); migration `0001` rollback in the file comment + bootstrap SQL parity for dev (hardening #4); CSRF — DELETE has no body, so SameSite=Lax is its only line (confirm no SameSite drift); 404 byte-identical parity on all five new routes.

## Top 2 risks — Frontend (undo UX + edit surface)

1. **Undo toast must never overpromise + delete affordances respect ownership (US-402, DI-2).** The 5s undo is UI-only (OQ-6) — after dismissal there is NO recovery path (no trash UI until purge); the toast copy must not imply data is recoverable beyond the window, and edit-mode copy must state tail-truncation is permanent (OQ-4 disclosure). The delete control is hidden for non-owned conversations (AC.7) — server enforces regardless, UI is defense-in-depth. Restore failure refetches the tree to true server state (AC.6) — no stale optimistic row lingering as if restored.
2. **XSS surface unchanged under new components (phase-3 T-T-1 carry-over).** Edit mode, delete dialogs, export menu, search input, shortcut overlay are all new React surfaces rendering user-derived strings — every one renders as React text children, zero `dangerouslySetInnerHTML`, no new markdown pipeline for edited content (it flows through the existing phase-3 renderer; user messages stay plain text). The CI grep gate extends to all phase-4 components. Tree search is client-only — the moment it "helpfully" gains a server fetch, it becomes a new endpoint needing its own ownership review (spec AC.7 asserts zero fetches; keep it that way).
